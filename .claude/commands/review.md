# 変更差分レビュー

現在のブランチの変更差分をレビューしてください。
**ファイルの編集・作成・削除、コミット、push は一切行わないでください。**
**テストやビルドの実行もしないでください。**
レビュー結果の報告だけを行います。

## 1. レビュー対象の特定

比較対象（BASE）は `$ARGUMENTS` です。空の場合は `main` を使います。

次のコマンドで差分を集めます。

- 未コミットの変更（ステージ済み + 未ステージ）: `git diff HEAD`
- 未追跡の新規ファイル: `git status --short` で `??` になっているファイルを確認し、中身は Read で読む（`git diff` には表示されないため）
- 現在のブランチが BASE と異なる場合のコミット済みの変更: `git diff BASE...HEAD` と `git log --oneline BASE..HEAD`

使い分けは次のとおりです。

- 現在のブランチが BASE と同じ（例: `main` 上で作業中）なら、未コミットの変更と未追跡ファイルだけを対象にします。
- 差分がまったくない場合は「レビュー対象の差分なし」と報告して終了します。

git が `dubious ownership` エラーで失敗した場合は、CLAUDE.md の「ローカル環境の注意」に従ってください。`git -c safe.directory=<リポジトリのパス> <コマンド>` の形で再実行し、グローバル設定は変更しません。

## 2. 前提の確認

- リポジトリのルートに `CLAUDE.md` があれば最初に読み、レビュー観点 9 の基準にします。
- 差分の行だけで判断せず、必要に応じて変更されたファイル全体と、呼び出し元・呼び出し先を Read / Grep で確認します。
- 秘密情報（`terraform.tfvars`、`*.tfstate`、`*.pem`、パスワードや署名鍵の値など）は、出力に値を書き写しません。

## 3. レビュー観点

1. **バグ・ロジックエラー**: 条件分岐、境界値（0・負数・null）、例外の扱い、null 安全性、数値のオーバーフロー
2. **セキュリティ**: 認証・認可（`SecurityConfig`、`@PreAuthorize`）、入力検証の漏れ、秘密情報の直書きやログへの出力、例外メッセージによる情報漏えい
3. **データ整合性**: 在庫の増減、注文時の価格保持、状態遷移（`OrderStatus`）、同時に更新されたときの不整合
4. **トランザクション**: `@Transactional` の有無と範囲、途中で失敗したときのロールバック、同じクラス内の呼び出しで `@Transactional` が効かないケース
5. **JPA / DB アクセス**: N+1 問題、LAZY / EAGER の設定、Entity 変更によるスキーマへの影響（`ddl-auto=update`）、`@Query` の正しさ、循環参照によるシリアライズの問題
6. **API 設計**: HTTP メソッドとステータスコード、既存のエラーレスポンス形式との一貫性、Entity をそのまま返すことの影響、後方互換性
7. **テスト不足**: 変更した振る舞いに対応するテストがあるか、異常系・境界値、Service が呼ばれないことの確認、既存テストへの影響
8. **可読性・保守性**: 命名、重複、責任の分け方、既存コードのスタイル（Lombok、コメント、インデント）との一貫性、不要な変更の混入
9. **CLAUDE.md のルール違反**: コーディング規約・テスト方針・慎重に扱うべきファイルへの変更・禁止事項など、CLAUDE.md に書かれたルールに照らして確認します（CLAUDE.md がなければ「CLAUDE.md なし」と記載）

## 4. 判断の基準

- **推測で断定しないこと。** コードから確認できた事実は「問題」として書きます。確認しきれないものは「要確認」と明記し、何を確認すれば判断できるかを書きます。
- 差分と関係のない既存の問題は、指摘の一覧に混ぜず、末尾の「差分外の既存の問題（参考）」に分けて書きます。
- 重要度の基準は次のとおりです。
  - **High**: 本番での不具合、データの破損や不整合、セキュリティ上の欠陥、ビルドやテストが失敗するもの
  - **Medium**: 特定の条件で誤動作するもの、テストが不足しているもの、API の一貫性を崩すもの、CLAUDE.md の重要なルールに違反しているもの
  - **Low**: 可読性やスタイル、軽い改善提案

## 5. 出力形式

最初に概要を書きます。

```
## レビュー概要
- 比較対象: <BASE または「未コミットの変更」>
- 対象ファイル: <ファイル一覧（新規 / 変更 / 削除）>
- 指摘件数: High n / Medium n / Low n
```

指摘は重要度の高い順に、1件ずつ次の形式で書きます。

```
### [High|Medium|Low] <短いタイトル>
- ファイル: `path/to/File.java:行番号`（行番号が特定できない場合はファイル名のみ）
- 観点: <1〜9 のどれか>
- 問題点: <何が起きているか>
- なぜ問題なのか: <どんな入力や状態で、どんな悪い結果になるか>
- 改善案: <具体的な修正方針（コードは提案にとどめ、適用しない）>
- 確度: 確認済み / 要確認（要確認の場合は確認方法）
```

最後に以下を書きます。

- **観点別の結果**: 1〜9 の各観点について、指摘があったか、「問題なし」かを1行ずつ書きます。
- High の指摘がない場合は、**「重大な問題なし」** と明記します。
- 指摘が1件もない場合は、「重大な問題なし（指摘事項なし）」と書きます。
- 必要なら「差分外の既存の問題（参考）」を書きます。
