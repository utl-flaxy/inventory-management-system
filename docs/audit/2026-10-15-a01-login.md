## 実コードの再評価

| 指摘 | 成立条件・実コードでの評価 |
|---|---|
| 特定usernameの5回試行で他者が429 | 正規利用者と攻撃者が同じ識別済みIP、または未設定proxyによる共通peerになった場合に成立。正しく分離した別IPにはpair枠は共有されず、アカウント全体のロックではない |
| Docker peerの共有 | host Caddy → loopback publish → appのpeerがgateway等になる場合、空のtrusted-proxiesでは共有。本番の実peerは未確認であり事故発生とは断定しない |
| global枠の消費 | 接続元を分離しても全受付（成功/失敗）が1000/分の全体枠を消費。source=100/分なので単一の独立IPだけで直ちに1000を消費するわけではないが、複数の実接続元で枠を使えば別の正常clientも拒否される |
| unknown / malformed | filter欠落・無効peerはunknown、不正な信頼済みproxy headerはpeerへ戻る。共通keyになる。ただし現CaddyはForwardedを除去しXFFを生成するため、外部clientがそのまま任意のForwardedを通せるとの主張は成立しない |
| 偽装XFF | 既存実装も未信頼peerのheaderを接続元として採用しない。この防御は維持 |
| カウンター容量 | 古い方式は満杯の履歴が期限切れになるまで、新規client全体に429を返す。global枠だけの撤去ではこの問題が残る |

## 独立した修正前プローブ

新しい受入テストを修正前コードで実行し、次の2件が意図した失敗となることを確認した。

- `completedAttackerFailuresCannotSpendAProcessWideMinuteBudgetForAnotherClient`:
  テスト設定global=10に対し、5接続元から各2回の失敗後、別接続元の正しい資格情報が
  **expected 200 / actual 429**。
- `malformedTrustedProxyClaimsDoNotAllocateSharedPeerQuota`:
  信頼済みpeerの予期しないForwardedに対し、**expected 503 / actual 401**。
  転送情報の不成立が共有peerでの認証まで進んでいた。

実MariaDBとembedded prod HTTPで実行。Claudeの結果を無条件には採用していない。
修正前ログはリポジトリ外の検証領域に保持し、資格情報をPRや証跡へ転載しない。

## 採用した設計

- prodは実測・完全一致のtrusted-proxies必須。DB初期化前に空・不正・保護無効化・native forwardingを拒否。
- 確認できないlogin sourceは503 ProblemDetail。共通peer/unknownを代用せず、DB/BCryptに進めない。
- sourceとsource＋usernameの枠は維持。1つのsource window配下で期限を揃え、case変更で枠をリセットしない。
- 時間窓のglobal-limitを、認証処理中だけ保持するmax-concurrentへ置換。満杯時は待機せず429・Retry-After: 1。
  既存global-limit設定は無視せず起動エラー。全exitでpermitを一度だけ解放。
- 保管領域が満杯なら別の最古source窓を配下keyごと退避。同一sourceのusername変更では自分の枠を退避できない。
  全体履歴の満杯だけで新規利用者を止めず、同時処理枠は独立して維持。
- RequestCorrelation → transport capture → Spring forwardingの順を明示。
- Docker動的検証は専用の使い捨てJDK probeで今回のpublish経路のpeerを実測。アプリimageへJDKを戻さず、
  IP値をartifactへ保存せず、新しいnetwork/containerだけを所有label確認後に片付ける。
- 公開register、一般業務API、JWT、role、DB schema/migration、Deploy/AWS境界は維持。
  既存productionテストの設定追加は、新しいfail-fast要件を満たして同じ回帰検証を継続するため。

## 残余リスクと運用上の前提

- 同一public NATを共有する攻撃者と正常利用者をIPだけで区別できない。
- 分散した実接続元が多数あれば履歴退避で試行枠がリセットされ得る。厳密な分散レート保証ではない。
- 分散攻撃で同時枠を占有し続ければ正常clientも一時429になる。ネットワーク/エッジの接続・送信元防御は別途必要。
- 単一JVMのメモリ内状態で、再起動reset、複数JVM非共有。全DoS防御を達成したとは主張しない。
- hostや共有Docker networkへ到達できるプロセスは信頼境界内。Docker gatewayのIPだけでCaddyのidentityを証明しない。
- 本番の実peer、Caddy以外の到達経路、同時数の妥当性、異なる実clientでのloginは運用者の公開前確認事項。
  誤った非空peerではreadiness=UPでもlogin=503となる。readinessだけで設定を認定しない。
- 空設定は今回から起動/Compose解決を拒否するため、[設定・移行・復旧手順](../auth.md#運用者の設定移行復旧)を先に実施する。
- app-only rollbackは旧image・解決済みCompose・旧environmentを使い、DBを再作成しない。
  旧imageへ戻す場合は旧共有枠のリスクも復活する。
